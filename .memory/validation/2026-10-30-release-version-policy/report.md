# 버전 규칙 변경 검증

- 확정 순서: 다음 배포0.1 → 0.11 → 0.12 → 0.13. 기준0.1 뒤에 정수 배포 순번을 문자열로 붙인다.0.19 다음은0.110이며0.2/1.0 자동 승격은 없다. 기준 변경은 사용자 요청 때만 한다.
- 현재 실제 배포0.01-b는 유지. 다음 버전 메타데이터·운영 지침·발표용/관리용 최신 HTML을 갱신했다. 과거0.01v/b 파일과 게임 소스/자산은 변경하지 않았다. 배포/push 없음.
- `npm test -- --run tests/docs/release-docs.test.js tests/docs/management-model.test.js`:2파일14테스트 통과. 문자열 증가/큰 정수/다른 계열 거부, 실제 두 템플릿0.1 생성, 새 배포 준비/대기 상태 재시도/다음 배포0.11과 기존 보호 검사를 포함한다.
- `npm run docs:build`, `npm run docs:check` 통과. `release:prepare -- --new-release --dry-run`은 현재0.01-b/준비 예정0.1을 반환하며 파일을 변경하지 않는다.
- `verify.mjs`:두 HTML의 현재/다음 버전, Downloads 동일성, 보존 파일 SHA256, 아직0.1 실제 릴리스 파일을 만들지 않았음을 확인.

## 구현·학습 노트

- 핵심 변경: `nextVersion(version, baseVersion='0.1')`가 부동소수점 대신 `BigInt(sequence)+1n`으로 배포 순번을 올린다. 카탈로그의 `versionBase`와 `nextVersion`을 두 HTML이 함께 읽는다.
- 알아야 할 점: 문서만 재생성할 때는 버전이 오르지 않는다. 실제 새 배포 요청은 `--new-release`로 준비하며 같은 소스여도 직전 버전이 배포 완료면 증가한다. 이미 배포 대기 중인 같은 소스의 재시도는 중복 증가하지 않는다.
- 함께 처리한 필수 부분: 이전 초기화 스크립트가 기존 카탈로그를 옛 규칙으로 덮어쓰지 못하게 막았다. dry-run은 실제 다음 후보와 이번 명령의 준비 결과를 분리해 표시한다. 범위 밖 게임 변경은 없으며 다른 특이사항 없음.
